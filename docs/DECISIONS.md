# Decisions

Решения, которых нет в CLAUDE.md. Одна строка: решение и причина.

- TypeScript 6.0.x вместо 7.x: `typescript-eslint` 8.71 (latest и canary) требует `typescript <6.1`, а у TS 7 нет классического Compiler API, на котором держится typed linting (`strictTypeChecked`). Один компилятор на весь репозиторий, чтобы `tsc` и ESLint понимали типы одинаково.
- Сервер и скрипты исполняются Node 24 напрямую из `.ts` (встроенный type stripping), без `tsx` и без сборки сервера: меньше инструментов и нет расхождения между dev и prod. Цена: только стираемый синтаксис (`erasableSyntaxOnly`), относительные импорты с расширением `.ts`.
- `@funnel/shared` экспортирует исходники (`exports: ./src/index.ts`): его потребляют Vite, Vitest и Node с type stripping, отдельная сборка пакета не нужна.
- pnpm 11: build-скрипты разрешаются через `allowBuilds` в `pnpm-workspace.yaml` (замена `onlyBuiltDependencies`): разрешены только `esbuild` и `lefthook`, `better-sqlite3` запрещён явно (см. ниже про готовые N-API бинарники).
- Корневой `vitest.config.ts` с `test.projects` вместо `vitest.workspace.ts`: workspace-файл в Vitest 4+ удалён, `projects` — его замена; пороги покрытия заданы по glob на пакет.
- Зависимости добавляются в той же задаче, что и код, который их использует: `knip` падает на неиспользуемых зависимостях, так что заранее установленный «набор на будущее» ломал бы ворота.
- Stylelint `declaration-strict-value`: функции (`color-mix()`, `linear-gradient()`) разрешены, но сырые литералы цветов, радиусов, теней и шрифтов вне `tokens.css` запрещены.
- Сырые цвета запрещены Stylelint в любом свойстве и внутри любой функции (`color-no-hex`, `color-named`, `function-disallowed-list` для rgb/hsl/oklch/…); `color-mix()` и градиенты разрешены, но только поверх `var(--…)`. Шорткат `font` запрещён вне `tokens.css`, чтобы `font-family` всегда проверялся.
- `apps/server/src/main.ts` исключён из покрытия: это только склейка процесса (env → БД → listen → сигналы), его поведение проверяют e2e и healthcheck на Railway.
- `lint:deps` охватывает `scripts/` и `e2e/` с той задачи, где эти папки появляются (depcruise падает на несуществующем пути).
- Stylelint `lightness-notation`, `hue-degree-notation` и `alpha-value-notation` выключены (и `custom-property-empty-line-before`, чтобы группировать токены): токены OKLCH переносятся из эталона один в один (`oklch(0.925 0.014 258)`), а не переписываются в проценты и градусы.
- `tokens.css` = `:root` эталона один в один плюс три осознанных отличия: в `--font` первым стоит `'Plus Jakarta Sans Variable'` (имя семейства в npm-пакете fontsource), добавлены `--on-ink` (текст на чёрном, вместо `#fff` в эталоне) и `--focus-ring` (цвет фокуса, в эталоне был инлайн `color-mix`).
- Страница `/admin/*` (SPA) пока отдаётся без Basic Auth, защищены только админские API. В Фазе 5 решить: guard на страницу или явная запись почему нет (данных страница без API не содержит).
- Контейнер работает от root: Railway монтирует volume с владельцем root, отдельный пользователь потребовал бы chown при каждом старте. `RAILWAY_RUN_UID=0` задан явно как страховка (§2).
- Проверка прода после деплоя — отдельный workflow `verify-deploy.yml` на событии `deployment_status` (Railway создаёт GitHub deployment `funnel-runtime / production`), а не job в `ci.yml`: Railway «Wait for CI» ждёт workflow, запущенные push в ветку, и проверка прода внутри push-CI заблокировала бы деплой навсегда.
- Stop-хук пропускает `pnpm check`, если отпечаток дерева (HEAD + `git diff HEAD` + неотслеживаемые файлы с содержимым) совпадает с последним зелёным прогоном. Строгость та же: любое изменение байта запускает полную проверку.
- Счётчики находок ревьюера берутся из комментариев PR скриптом `pnpm review:stats`. Последняя строка комментария ревьюера считает только новые находки раунда. Комментарий раунда 2 у #18 (до этого правила) включал 2 открытые находки в счёт, поэтому minors у #18 завышены на 2 (скрипт даёт 12, новых было 10).
- `better-sqlite3` 13 поставляет готовые N-API бинарники внутри npm-пакета (`prebuilds/`), поэтому его build-скрипт запрещён (`allowBuilds: better-sqlite3: false`). Иначе pnpm запускает неявный `node-gyp rebuild` из-за `binding.gyp` и компилирует SQLite из исходников, а это требует тулчейна в CI, в контейнере Playwright и в Docker. Без сборки тулчейн не нужен нигде.
- `knip`: для `packages/shared` выключен `includeEntryExports`. Публичный API `@funnel/shared` (`src/index.ts`) замораживается в Фазе 1, раньше, чем появляются его потребители (сервер, веб, генератор). Экспорты внутренних модулей по-прежнему проверяются: они должны использоваться через `index.ts` или тестами. В Фазе 6 проверку вернуть (#39).
- Прогресс воронки считает только видимые шаги известных типов, не входящие в `progress.excludeTypes`. Шаг неизвестного типа показывается заглушкой «continue» (§8.2), а не вопросом, поэтому в «N of M» не входит.
- `validateAnswer` знает ещё один код, `invalidType` (кроме семи из §4.5): значение не той формы (строка для числового шага, не массив для multi-select, `NaN`). Ответы приходят из JSON, и без отдельного кода такое значение пришлось бы выдавать за «нет ответа».
- Вопрос обязателен, если в конфиге нет явного `validation.required: false`: шаг без блока `validation` тоже нужно ответить, иначе `POST /complete` пропускал бы его молча. Необязательный multi-select с `minSelections` принимает пустой выбор, а минимум проверяется, только если что-то выбрано.
- Номер версии и `funnelId` линт сверяет с сохранёнными версиями только при загрузке (`existing`). При публикации черновик уже проверен, а черновики, загруженные позже, не должны его блокировать. Повторная загрузка с тем же `config_hash` возвращает существующую версию до линта, поэтому остаётся идемпотентной.
- Предупреждения линта об изменениях относительно активной версии (шаг удалён из варианта, новый или удалённый результат, новое или удалённое событие) строятся из `diffConfigs`, а не отдельной логикой линта: список изменений определяется в одном месте.
- `events.privacy.allowAnswerKinds: false` исключает `answer_kind` из whitelist событий. Значения свойств проверяются после whitelist: лишний ключ с вложенным значением отбрасывается и помечается (`dropped_props`), а не роняет событие; `answer_kind` с чем-либо, кроме формы ответа, тоже отбрасывается.
- HTTP-контракт фаз 2–5 (`shared/api/contract.ts`) и форма ответа аналитики (`shared/analytics/summary.ts`) заморожены в конце Фазы 1, до реализации. Меняются только аддитивно (новые поля и маршруты), каждое изменение — строка здесь. Схемы ответов без трансформаций: сервер кодирует ответы через `z.encode`, а трансформация ломает кодирование (поэтому есть `ParsedStepSchema`).
- Загрузка конфига (`POST /api/admin/versions`) отклоняет 422 только ошибки схемы и те ошибки линта, с которыми версию нельзя сохранить (`funnel_id`, `version_order`: конфликт с сохранёнными версиями). Остальные ошибки линта сохраняются вместе с черновиком и блокируют публикацию: админ видит их в «Review changes», а не только в ответе на загрузку.
- Активная версия и разобранные конфиги кешируются в памяти сервиса версий; кеш активной версии сбрасывается при каждой записи в журнал активаций. Это корректно, потому что инстанс один (CLAUDE.md §2), а версии неизменяемы.
- `pnpm seed` — тот же модуль `apps/server/src/db/seed.ts`, запущенный как скрипт (`import.meta.main`): функция и её CLI в одном файле, отдельной точки входа нет.
- Публикация не сверяет номер версии с другими версиями: номер упорядочивает загрузки, а порядок активаций хранит журнал. Старый черновик можно опубликовать после нового (например, отказаться от v3 и выкатить v2); `fromVersion` в журнале покажет, откуда пришли.
- `engines.node` — `>=24.2 <25`: `pnpm seed` запускает модуль через `import.meta.main`, который появился в Node 24.2.
- Откат (`POST /api/admin/rollback`) активирует `fromVersion` последней строки журнала: это отмена последнего переключения. Повторный откат возвращает обратно (v2 → v1 → v2), а не идёт дальше вглубь истории; для произвольной версии есть `activate`.
- Админский API версий работает с единственной воронкой в базе (маршруты без `funnelId`): загрузка отклоняет конфиг с другим `funnelId` (линт `funnel_id`), поэтому вторая воронка в базу не попадает.
- Fastify передаёт отсутствующее тело запроса валидатору как `null`, а `.default({})` в zod срабатывает только на `undefined`; `plugins/route.ts` превращает `null` в `undefined` перед схемой, и `POST /publish`, `/activate`, `/rollback` работают без тела.
- `assignVariant`: FNV-1a считается по UTF-8 байтам строки `sessionId:experimentId`; если веса вариантов в сумме не 100, пороги масштабируются на их сумму (`1:3` даёт 25/75). Линт гарантирует только положительные веса, а не сумму 100.
- Сессия с `variantOverride` всегда `traffic_type='qa'`, даже если генератор прислал `trafficType: 'synthetic'` с ключом: override — ручная проверка варианта, и такие сессии должны прятаться фильтром QA (§9.1: «4 сессии с override, по умолчанию не видны»). Ключ генератора при этом всё равно проверяется.
- Rate limit включается на маршруте опцией `route(..., { rateLimit })`, а не глобально; лимит `POST /api/sessions` — `RATE_LIMIT_SESSIONS` (по умолчанию 30 в минуту на IP). Запросы с верным `X-Generator-Key` от лимита освобождены: генератор законно создаёт сотни сессий с одного адреса.
- `buildApp` принимает общие сервисы (`createSharedServices`): сервис версий кеширует активную версию и сбрасывает кеш только на своих записях, поэтому тест, публикующий версию, обязан работать через тот же экземпляр, что и приложение (`t.services.versions`).
- Резолвнутый конфиг кешируется в сервисе сессий по ключу (funnelId, version, variant): версии неизменяемы, а `resolveFunnel` вызывается на каждый `GET` сессии.
- IP клиента для rate limit берётся из заголовка, который ставит сам edge платформы (`CLIENT_IP_HEADER`, в production по умолчанию `x-real-ip`: Railway документирует его как IP клиента), иначе из адреса сокета. `trustProxy` выключен: левую часть `X-Forwarded-For` присылает клиент, и с `trustProxy: true` лимит обходился подменой заголовка (находка ревью #64).
- `buildApp` требует общие сервисы явным параметром: экземпляр сервиса версий с собственным кешем нельзя создать по ошибке.
- `PUT /api/sessions/:id/state` проверяет каждый ответ в `answers` через `validateAnswer`, включая ответы шагов, ставших скрытыми (они хранятся, §4.4, значит, должны быть валидными). Следствие для клиента (Фаза 3): незаконченный ввод (пустой multi-select, число вне диапазона) живёт только в локальном состоянии шага и в `answers` не попадает до валидного Continue.
- Ошибки 422 состояния и завершения несут в `details` только `{ stepId, code }` или `{ answer: <ключ> }`, а сообщение берётся из `validation.messages` конфига: значение ответа не попадает ни в ответ API, ни в лог (§5, §7.2).
- `POST /complete` идемпотентен в сильном смысле: если `result_id` уже сохранён, он возвращается без пересчёта, даже если состояние потом менялось. Сохранение состояния после завершения не запрещено (пользователь может вернуться назад), но результат сессии остаётся первым вычисленным: аналитика видит один результат на сессию.
- Контракт (аддитивно): `SessionUnprocessableDetailsSchema` — форма `error.details` у 422 на `saveState` и `completeSession` (`{ stepId, code? }` или `{ answer }`), чтобы клиент Фазы 3 не описывал её вручную.
- Оптимистическая блокировка состояния сессии проверяется и в SQL (`UPDATE … WHERE state_rev = baseRev`), а не только в сервисе: корректность не зависит от того, что между чтением и записью нет `await`.
- Пустые и пробельные UTM-значения (`?utm_campaign=`) хранятся как `NULL`, а не `''`: иначе фильтр по кампании и вырез источников в дашборде показали бы пустую кампанию.
- Контракт (аддитивно): `code` в 422-деталях сессий — `z.enum(VALIDATION_CODES)`; список кодов валидации экспортирован как кортеж в `engine/validation.ts`, тип `ValidationCode` выводится из него.
- `tokens.css` (аддитивно): радиусы и тени, которые эталон пишет инлайн (карточка воронки 32/26px, опции 16px, поле числа 20px, обводки `inset 0 0 0 1px` и 1.5px), получили имена токенов (`--r-glass`, `--r-option`, `--ring-line`, `--ring-ink`, `--shadow-glass` и т. д.): Stylelint запрещает сырые радиусы и тени вне `tokens.css`, а значения остаются эталонными.
- Веб-клиент API (`lib/api.ts`) бросает тот же `DomainError` из `@funnel/shared`, что и сервер: код и `details` из конверта ошибки, сетевой сбой — `unavailable`, ответ без конверта (страница прокси) — код по HTTP-статусу. Ответ разбирается схемой маршрута из контракта, несовпадение — `internal`. `details` типизируются схемой из `contract.<route>.errorDetails`.
- У `apps/web` есть Vitest-проект для чистых модулей (редьюсер, клиент API, хелперы) в Node-окружении со стабами браузерных глобалов; компоненты проверяет Playwright. Порог покрытия на `apps/web` не вводится (§3.1: веб покрывается e2e).
- Контракт (аддитивно): `codeForStatus(status)` в `shared/api/errors.ts` — обратное отображение `ERROR_STATUS` для ответов без конверта ошибки (страница прокси), прочие 5xx → `unavailable`. Клиент не держит свою копию таблицы статусов.
- Префикс `-webkit-backdrop-filter` в исходниках не пишется: Stylelint запрещает вендорные префиксы, а сборка (Lightning CSS в Vite) добавляет его сама — в `dist` есть оба объявления.
- Незаконченный ввод шага живёт в `draft` чистого `funnelReducer`, а не в `answers`: в `answers` (и на сервер) ответ попадает только при валидном Continue. Так редьюсер целиком тестируется, а сервер никогда не получает невалидный ответ. Прогресс считается с учётом валидного `draft`, чтобы total менялся сразу при выборе ответа, открывающего шаг (§8.2).
- `step_viewed.visible_step_index` — позиция шага в видимом пути с 1, `visible_step_count` — длина видимого пути целиком (с intro и result): это свойства пути, а не прогресс-бара, который считает только вопросы.
