# Decisions

Решения, которых нет в CLAUDE.md. Одна строка: решение и причина.

- TypeScript 6.0.x вместо 7.x: `typescript-eslint` 8.71 (latest и canary) требует `typescript <6.1`, а у TS 7 нет классического Compiler API, на котором держится typed linting (`strictTypeChecked`). Один компилятор на весь репозиторий, чтобы `tsc` и ESLint понимали типы одинаково.
- Сервер и скрипты исполняются Node 24 напрямую из `.ts` (встроенный type stripping), без `tsx` и без сборки сервера: меньше инструментов и нет расхождения между dev и prod. Цена: только стираемый синтаксис (`erasableSyntaxOnly`), относительные импорты с расширением `.ts`.
- `@funnel/shared` экспортирует исходники (`exports: ./src/index.ts`): его потребляют Vite, Vitest и Node с type stripping, отдельная сборка пакета не нужна.
- pnpm 11: build-скрипты разрешаются через `allowBuilds` в `pnpm-workspace.yaml` (замена `onlyBuiltDependencies`): разрешены только `esbuild` и `lefthook`, `better-sqlite3` запрещён явно (см. ниже про готовые N-API бинарники).
- Корневой `vitest.config.ts` с `test.projects` вместо `vitest.workspace.ts`: workspace-файл в Vitest 4+ удалён, `projects` — его замена; пороги покрытия заданы по glob на пакет.
- Зависимости добавляются в той же задаче, что и код, который их использует: `knip` падает на неиспользуемых зависимостях, так что заранее установленный «набор на будущее» ломал бы ворота.
- Stylelint `declaration-strict-value`: функции (`color-mix()`, `linear-gradient()`) разрешены, но сырые литералы цветов, радиусов, теней и шрифтов вне `tokens.css` запрещены.
- Сырые цвета запрещены Stylelint в любом свойстве и внутри любой функции (`color-no-hex`, `color-named`, `function-disallowed-list` для rgb/hsl/oklch/…); `color-mix()` и градиенты разрешены, но только поверх `var(--…)`. Шорткат `font` запрещён вне `tokens.css`, чтобы `font-family` всегда проверялся.
- `apps/server/src/main.ts` исключён из покрытия: это только склейка процесса (env → БД → listen → сигналы), его поведение проверяют e2e и healthcheck на Railway.
- `lint:deps` охватывает `scripts/` и `e2e/` с той задачи, где эти папки появляются (depcruise падает на несуществующем пути).
- Stylelint `lightness-notation`, `hue-degree-notation` и `alpha-value-notation` выключены (и `custom-property-empty-line-before`, чтобы группировать токены): токены OKLCH переносятся из эталона один в один (`oklch(0.925 0.014 258)`), а не переписываются в проценты и градусы.
- `tokens.css` = `:root` эталона один в один плюс три осознанных отличия: в `--font` первым стоит `'Plus Jakarta Sans Variable'` (имя семейства в npm-пакете fontsource), добавлены `--on-ink` (текст на чёрном, вместо `#fff` в эталоне) и `--focus-ring` (цвет фокуса, в эталоне был инлайн `color-mix`).
- Страница `/admin/*` (SPA) пока отдаётся без Basic Auth, защищены только админские API. В Фазе 5 решить: guard на страницу или явная запись почему нет (данных страница без API не содержит).
- Контейнер работает от root: Railway монтирует volume с владельцем root, отдельный пользователь потребовал бы chown при каждом старте. `RAILWAY_RUN_UID=0` задан явно как страховка (§2).
- Проверка прода после деплоя — отдельный workflow `verify-deploy.yml` на событии `deployment_status` (Railway создаёт GitHub deployment `funnel-runtime / production`), а не job в `ci.yml`: Railway «Wait for CI» ждёт workflow, запущенные push в ветку, и проверка прода внутри push-CI заблокировала бы деплой навсегда.
- Stop-хук пропускает `pnpm check`, если отпечаток дерева (HEAD + `git diff HEAD` + неотслеживаемые файлы с содержимым) совпадает с последним зелёным прогоном. Строгость та же: любое изменение байта запускает полную проверку.
- Счётчики находок ревьюера берутся из комментариев PR скриптом `pnpm review:stats`. Последняя строка комментария ревьюера считает только новые находки раунда. Комментарий раунда 2 у #18 (до этого правила) включал 2 открытые находки в счёт, поэтому minors у #18 завышены на 2 (скрипт даёт 12, новых было 10).
- `better-sqlite3` 13 поставляет готовые N-API бинарники внутри npm-пакета (`prebuilds/`), поэтому его build-скрипт запрещён (`allowBuilds: better-sqlite3: false`). Иначе pnpm запускает неявный `node-gyp rebuild` из-за `binding.gyp` и компилирует SQLite из исходников, а это требует тулчейна в CI, в контейнере Playwright и в Docker. Без сборки тулчейн не нужен нигде.
- `knip`: для `packages/shared` выключен `includeEntryExports`. Публичный API `@funnel/shared` (`src/index.ts`) замораживается в Фазе 1, раньше, чем появляются его потребители (сервер, веб, генератор). Экспорты внутренних модулей по-прежнему проверяются: они должны использоваться через `index.ts` или тестами. В Фазе 6 проверку вернуть (#39).
- Прогресс воронки считает только видимые шаги известных типов, не входящие в `progress.excludeTypes`. Шаг неизвестного типа показывается заглушкой «continue» (§8.2), а не вопросом, поэтому в «N of M» не входит.
- `validateAnswer` знает ещё один код, `invalidType` (кроме семи из §4.5): значение не той формы (строка для числового шага, не массив для multi-select, `NaN`). Ответы приходят из JSON, и без отдельного кода такое значение пришлось бы выдавать за «нет ответа».
- Вопрос обязателен, если в конфиге нет явного `validation.required: false`: шаг без блока `validation` тоже нужно ответить, иначе `POST /complete` пропускал бы его молча. Необязательный multi-select с `minSelections` принимает пустой выбор, а минимум проверяется, только если что-то выбрано.
- Номер версии и `funnelId` линт сверяет с сохранёнными версиями только при загрузке (`existing`). При публикации черновик уже проверен, а черновики, загруженные позже, не должны его блокировать. Повторная загрузка с тем же `config_hash` возвращает существующую версию до линта, поэтому остаётся идемпотентной.
- Предупреждения линта об изменениях относительно активной версии (шаг удалён из варианта, новый или удалённый результат, новое или удалённое событие) строятся из `diffConfigs`, а не отдельной логикой линта: список изменений определяется в одном месте.
- `events.privacy.allowAnswerKinds: false` исключает `answer_kind` из whitelist событий. Значения свойств проверяются после whitelist: лишний ключ с вложенным значением отбрасывается и помечается (`dropped_props`), а не роняет событие; `answer_kind` с чем-либо, кроме формы ответа, тоже отбрасывается.
- HTTP-контракт фаз 2–5 (`shared/api/contract.ts`) и форма ответа аналитики (`shared/analytics/summary.ts`) заморожены в конце Фазы 1, до реализации. Меняются только аддитивно (новые поля и маршруты), каждое изменение — строка здесь. Схемы ответов без трансформаций: сервер кодирует ответы через `z.encode`, а трансформация ломает кодирование (поэтому есть `ParsedStepSchema`).
- Загрузка конфига (`POST /api/admin/versions`) отклоняет 422 только ошибки схемы и те ошибки линта, с которыми версию нельзя сохранить (`funnel_id`, `version_order`: конфликт с сохранёнными версиями). Остальные ошибки линта сохраняются вместе с черновиком и блокируют публикацию: админ видит их в «Review changes», а не только в ответе на загрузку.
- Активная версия и разобранные конфиги кешируются в памяти сервиса версий; кеш активной версии сбрасывается при каждой записи в журнал активаций. Это корректно, потому что инстанс один (CLAUDE.md §2), а версии неизменяемы.
- `pnpm seed` — тот же модуль `apps/server/src/db/seed.ts`, запущенный как скрипт (`import.meta.main`): функция и её CLI в одном файле, отдельной точки входа нет.
- Публикация не сверяет номер версии с другими версиями: номер упорядочивает загрузки, а порядок активаций хранит журнал. Старый черновик можно опубликовать после нового (например, отказаться от v3 и выкатить v2); `fromVersion` в журнале покажет, откуда пришли.
- `engines.node` — `>=24.2 <25`: `pnpm seed` запускает модуль через `import.meta.main`, который появился в Node 24.2.
- Откат (`POST /api/admin/rollback`) активирует `fromVersion` последней строки журнала: это отмена последнего переключения. Повторный откат возвращает обратно (v2 → v1 → v2), а не идёт дальше вглубь истории; для произвольной версии есть `activate`.
- Админский API версий работает с единственной воронкой в базе (маршруты без `funnelId`): загрузка отклоняет конфиг с другим `funnelId` (линт `funnel_id`), поэтому вторая воронка в базу не попадает.
- Fastify передаёт отсутствующее тело запроса валидатору как `null`, а `.default({})` в zod срабатывает только на `undefined`; `plugins/route.ts` превращает `null` в `undefined` перед схемой, и `POST /publish`, `/activate`, `/rollback` работают без тела.
- `assignVariant`: FNV-1a считается по UTF-8 байтам строки `sessionId:experimentId`; если веса вариантов в сумме не 100, пороги масштабируются на их сумму (`1:3` даёт 25/75). Линт гарантирует только положительные веса, а не сумму 100.
- Сессия с `variantOverride` всегда `traffic_type='qa'`, даже если генератор прислал `trafficType: 'synthetic'` с ключом: override — ручная проверка варианта, и такие сессии должны прятаться фильтром QA (§9.1: «4 сессии с override, по умолчанию не видны»). Ключ генератора при этом всё равно проверяется.
- Rate limit включается на маршруте опцией `route(..., { rateLimit })`, а не глобально; лимит `POST /api/sessions` — `RATE_LIMIT_SESSIONS` (по умолчанию 30 в минуту на IP). Запросы с верным `X-Generator-Key` от лимита освобождены: генератор законно создаёт сотни сессий с одного адреса.
- `buildApp` принимает общие сервисы (`createSharedServices`): сервис версий кеширует активную версию и сбрасывает кеш только на своих записях, поэтому тест, публикующий версию, обязан работать через тот же экземпляр, что и приложение (`t.services.versions`).
- Резолвнутый конфиг кешируется в сервисе сессий по ключу (funnelId, version, variant): версии неизменяемы, а `resolveFunnel` вызывается на каждый `GET` сессии.
- IP клиента для rate limit берётся из заголовка, который ставит сам edge платформы (`CLIENT_IP_HEADER`, в production по умолчанию `x-real-ip`: Railway документирует его как IP клиента), иначе из адреса сокета. `trustProxy` выключен: левую часть `X-Forwarded-For` присылает клиент, и с `trustProxy: true` лимит обходился подменой заголовка (находка ревью #64).
- `buildApp` требует общие сервисы явным параметром: экземпляр сервиса версий с собственным кешем нельзя создать по ошибке.
- `PUT /api/sessions/:id/state` проверяет каждый ответ в `answers` через `validateAnswer`, включая ответы шагов, ставших скрытыми (они хранятся, §4.4, значит, должны быть валидными). Следствие для клиента (Фаза 3): незаконченный ввод (пустой multi-select, число вне диапазона) живёт только в локальном состоянии шага и в `answers` не попадает до валидного Continue.
- Ошибки 422 состояния и завершения несут в `details` только `{ stepId, code }` или `{ answer: <ключ> }`, а сообщение берётся из `validation.messages` конфига: значение ответа не попадает ни в ответ API, ни в лог (§5, §7.2).
- `POST /complete` всегда пересчитывает результат по текущему сохранённому состоянию и записывает его, только если он изменился: после Back и другого ответа результат на экране должен соответствовать ответам. Идемпотентность сохраняется (то же состояние — тот же результат, строка не переписывается). `result_id` — результат последнего завершённого состояния и при уходе с экрана результата не очищается: сессия, однажды дошедшая до результата, дошла (у неё есть `result_viewed`) и не считается активной; разбивку по результатам аналитика берёт из `sessions.result_id`, а `reachedResult` — из событий (решения оркестратора по ревью #98; раньше результат фиксировался первым вычислением).
- Контракт (аддитивно): `SessionUnprocessableDetailsSchema` — форма `error.details` у 422 на `saveState` и `completeSession` (`{ stepId, code? }` или `{ answer }`), чтобы клиент Фазы 3 не описывал её вручную.
- Оптимистическая блокировка состояния сессии проверяется и в SQL (`UPDATE … WHERE state_rev = baseRev`), а не только в сервисе: корректность не зависит от того, что между чтением и записью нет `await`.
- Пустые и пробельные UTM-значения (`?utm_campaign=`) хранятся как `NULL`, а не `''`: иначе фильтр по кампании и вырез источников в дашборде показали бы пустую кампанию.
- Контракт (аддитивно): `code` в 422-деталях сессий — `z.enum(VALIDATION_CODES)`; список кодов валидации экспортирован как кортеж в `engine/validation.ts`, тип `ValidationCode` выводится из него.
- `aggregate` принимает один объект `{ sessions, events, versions, ingest, filters, now }`, а не позиционные аргументы из §11.2: кроме сессий, событий, конфигов и фильтров ему нужны время (функция чистая) и счётчики приёма, которые не принадлежат ни одной сессии (дубли из `ingest_log`, отклонённые по причинам).
- Порог «in progress» (30 минут) применяется только к `live`. QA-сессии (override), как и синтетические, считаются завершёнными сразу: это ручные проверки, а не живые пользователи, которые ещё отвечают.
- Начатая сессия без единого шагового события считается достигшей первого шага последовательности (расширение implied reach: сессия создаётся, когда воронка рисует первый шаг) и ушедшей с него: так Started = reachedResult + In progress + Σ Dropped here, и Dropped here шага никогда не больше, чем reached − completed.
- Разбивка по результатам (`results`) берёт результат из `sessions.result_id` (его вычисляет и хранит сервер, §6.3), а не из `result_id` в клиентских событиях: клиент не может переложить сессию в другой результат, и порядок событий на разбивку не влияет.
- Шаг `result` в пошаговых метриках достигнут ровно тогда, когда достигнут результат (`result_viewed` или `cta_clicked`), и завершён тем же: дальше идти некуда, конверсию в CTA показывают отдельные метрики.
- A/B-сравнение (`experiment`) всегда считается по обоим вариантам выбранной версии, независимо от фильтра варианта: фильтр сужает KPI и шаги, а сравнение без второго варианта бессмысленно.
- `sources` (вырез с `utm_source`) не сужается фильтром по источнику: иначе после клика по источнику остальные пропали бы и переключиться было бы не на что.
- Флаги `out_of_order` и `context_mismatch` считаются по различным `eventId`: повтор строки во входе агрегатора (журнал генератора) не завышает качество данных.
- Списки кампаний и источников в `/api/analytics/filters` не включают значения, которые есть только у QA-сессий: по умолчанию QA скрыт, и такой пункт дал бы пустой дашборд.
- `tokens.css` (аддитивно): радиусы и тени, которые эталон пишет инлайн (карточка воронки 32/26px, опции 16px, поле числа 20px, обводки `inset 0 0 0 1px` и 1.5px), получили имена токенов (`--r-glass`, `--r-option`, `--ring-line`, `--ring-ink`, `--shadow-glass` и т. д.): Stylelint запрещает сырые радиусы и тени вне `tokens.css`, а значения остаются эталонными.
- Веб-клиент API (`lib/api.ts`) бросает тот же `DomainError` из `@funnel/shared`, что и сервер: код и `details` из конверта ошибки, сетевой сбой — `unavailable`, ответ без конверта (страница прокси) — код по HTTP-статусу. Ответ разбирается схемой маршрута из контракта, несовпадение — `internal`. `details` типизируются схемой из `contract.<route>.errorDetails`.
- У `apps/web` есть Vitest-проект для чистых модулей (редьюсер, клиент API, очередь событий, хелперы) в Node-окружении со стабами браузерных глобалов; компоненты проверяет Playwright (§3.1: веб покрывается e2e). Порог покрытия в вебе один — 85% строк на `eventQueue.ts`: очередь — чистая логика с ретраями и хранилищем, и e2e проходит не все её ветки.
- Контракт (аддитивно): `codeForStatus(status)` в `shared/api/errors.ts` — обратное отображение `ERROR_STATUS` для ответов без конверта ошибки (страница прокси), прочие 5xx → `unavailable`. Клиент не держит свою копию таблицы статусов.
- Префикс `-webkit-backdrop-filter` в исходниках не пишется: Stylelint запрещает вендорные префиксы, а сборка (Lightning CSS в Vite) добавляет его сама — в `dist` есть оба объявления.
- Незаконченный ввод шага живёт в `draft` чистого `funnelReducer`, а не в `answers`: в `answers` (и на сервер) ответ попадает только при валидном Continue. Так редьюсер целиком тестируется, а сервер никогда не получает невалидный ответ. Прогресс считается с учётом валидного `draft`, чтобы total менялся сразу при выборе ответа, открывающего шаг (§8.2).
- `step_viewed.visible_step_index` — позиция шага в видимом пути с 1, `visible_step_count` — длина видимого пути целиком (с intro и result): это свойства пути, а не прогресс-бара, который считает только вопросы.
- Контракт движка (аддитивно): `stepBack(history, to?)` — необязательный `to` снимает стек до последнего посещения этого шага (браузерная «назад» через несколько записей). Правило «назад только по истории» остаётся в одном месте.
- Необязательный вопрос, очищенный и пройденный Continue, удаляет свой старый ответ из `answers` и не шлёт `answer_submitted` (ответа нет), только `step_completed`.
- Состояние сессии сохраняется (`PUT .../state`) сразу при каждом переходе между шагами, без debounce 300 мс: `answers` меняются только при переходе (в них попадают только валидные ответы), поэтому между переходами сохранять нечего. Сохранения одной сессии идут строго по очереди (scope мутации TanStack Query), каждое с `baseRev` предыдущего успешного.
- Зеркало состояния в localStorage хранит ревизию, на которой оно основано, и флаг «не подтверждено сервером». При загрузке локальное состояние побеждает, только если оно не подтверждено и основано на текущей ревизии сервера (переход сделан, а сохранение не дошло); иначе побеждает сервер. Конфиг воронки в зеркало не кладётся: он приходит только с сессией (§6.4), поэтому после refresh шаг рисуется после `GET` сессии.
- Браузерная «назад» на посещённый шаг — это Back (`back_clicked`, без новой записи истории); любой другой URL (корень, устаревший или набранный руками адрес, «вперёд») заменяется текущим шагом сессии. Кнопка Back в карточке (и Esc, Alt+←) делает браузерную «назад» (`navigate(-1)`), если текущая запись истории помечена шагом, с которого на неё пришли (`history.state.from`), и это тот шаг, куда ведёт Back: тогда история воронки и браузера остаются одним стеком. Иначе (вкладка открыта сразу на шаге, запись заменена, предыдущая запись — админка) — Back с заменой текущей записи. Пока идёт переход между шагами (view transition асинхронен), любые действия игнорируются, а переход фиксирует ровно то состояние, которое сохранено и отправлено в события (действие `set`).
- Тон выбранного ответа смешивается в sRGB (`color-mix(in srgb, var(--a) 7%, var(--card))`): в OKLCH смесь с белым берёт его оттенок 0 и даёт розовый вместо голубого, который требует §10.
- Живая воронка показывает результат только из ответа `POST /complete` (пока он идёт — `loadingTitle`, при ошибке — `errorTitle` и `retryLabel`): оптимистичный `computeResult` мог бы на мгновение показать не тот результат и отправить `result_viewed` с чужим `result_id`. `computeResult` на клиенте использует только предпросмотр, где сервера нет. `complete` идёт в той же очереди мутаций, что и сохранения состояния, поэтому считается по последнему сохранённому состоянию.
- План на 30 дней — рекомендации результата по порядку, разложенные по четырём неделям (лишние попадают в четвёртую); код добавляет только подписи «Week N». `recommendation_expanded` отправляется при раскрытии плана только если событие есть в каталоге версии сессии (§8.4), и только со свойствами, выводимыми из CTA конфига (`result_id`, `action`): код не знает значений свойств, которые определяет будущий конфиг (решение оркестратора по ревью #98).
- Debug-оверлей на ширине до 720px идёт в потоке под карточкой, а не поверх: фиксированная плашка закрывала бы Continue на телефоне.
- Предпросмотр версии — маршрут `/admin/preview/:version?variant=A|B` вне админского каркаса Фазы 5: та же карточка воронки, состояние только в памяти (без localStorage и URL шагов), `NOOP_SINK` вместо очереди событий, результат считает `computeResult` на клиенте. Сеть — только `GET /api/admin/versions/:v/preview` (e2e проверяет, что нет ни одного не-GET запроса и число сессий не меняется).
- После перехода между шагами фокус переходит на тело нового шага (`tabIndex=-1`, layout-эффект, без кольца фокуса): скринридер начинает с заголовка шага, а Enter после клика по Back означает Continue, а не повторный Back (§8.2). 409 во время перехода отменяет его фиксацию (эпоха в `useFunnelMachine`), чтобы принятое состояние сервера не перезаписалось.
- E2E-фикстура (аддитивно): опция `allowedConsoleErrors` — тест, который сам вызывает ожидаемый HTTP-ответ с ошибкой (браузер пишет каждый 4xx/5xx в консоль), перечисляет его шаблон; все остальные ошибки консоли по-прежнему роняют тест.
- Фаза 5 строит админку на фундаменте Фазы 3 (токены, `lib/api.ts`, `ui/{Button,IconButton,Card,Toast,Icon}`), поэтому ветка Фазы 3 вливается в ветку Фазы 5 обычным merge-коммитом, а в `main` Фаза 3 вливается раньше Фазы 5.
- Ingest проверяет `step_id` по последовательности варианта закреплённой версии сессии, а не по всем шагам версии: клиент рисует только шаги своего варианта, а событие по шагу другого варианта — подделка или ошибка, его нельзя считать в пошаговой аналитике.
- `context_mismatch` по UTM ставится, только если клиент прислал непустое значение, отличное от сессии. Клиент может не знать UTM (после refresh их нет в URL, а ответ сессии их не содержит), и отсутствие поля — не ложное утверждение.
- События истёкшей сессии принимаются: сессия существует (§7.3), а outbox и `sendBeacon` законно досылают события после паузы. Истечение влияет только на восстановление ответов.
- В `rejected_events.raw_json` хранятся только известные поля события (`ClientEventSchema`), `properties` заменяется списком ключей, а элемент пачки, который не объект, — только своим JSON-типом; затем JSON обрезается до 4 КБ по границе символа UTF-8. Отклонённое событие могло нести сырой ответ, а приватность (§7.2) важнее полноты отладочной копии.
- `out_of_order` сравнивает `client_seq` с максимумом, уже принятым в сессии на момент вставки, включая события раньше в той же пачке; дубль на флаг не влияет, потому что его номер уже учтён.
- Лимит `POST /api/events/batch` — `RATE_LIMIT_EVENTS` (по умолчанию 120 в минуту на IP): вкладка флашит outbox раз в 2 секунды (≈30 запросов в минуту), запас — на несколько вкладок за одним NAT и `sendBeacon`. Генератор с ключом освобождён, как и на сессиях.
- Live events показывает результаты приёма пачек (`accepted` / `duplicate` / `rejected`), серверный `session_started` в поток не попадает: статусы в потоке — это статусы ingest, а начало сессии видно по первому `step_viewed`. Буфер — последние 50 записей в памяти процесса (инстанс один), новый подписчик получает их сразу при подключении.
- SSE-поток `GET /api/live` отдаётся через `reply.hijack()` (заголовки helmet, выставленные в `onRequest`, при этом сохраняются). Все открытые потоки закрываются в хуке `preClose`, иначе `app.close()` при SIGTERM ждал бы клиентов, которые сами не отключаются. Поток клиента, у которого в буфере скопилось больше 1 МБ неотправленных данных, закрывается: EventSource переподключится и получит последние 50 записей. Строковые поля отклонённых элементов (id, имя, шаг) обрезаются до 200 символов перед ответом, записью и трансляцией.
- Клиентская очередь событий: ответ 400 или 413 на пачку считается «ядовитым» — очередь делит пачку пополам и шлёт снова, а событие, которое сервер не принял и в одиночку, удаляет с предупреждением. Иначе одно слишком большое событие навсегда блокировало бы outbox. 429, 5xx, сетевая ошибка, нераспознанный ответ 200 и прочие коды — повтор с backoff 1, 2, 4, 8, 16, 30 с; после успеха backoff сбрасывается. Во время backoff новые события не ускоряют повтор.
- Очередь пишет outbox (`funnel:events:<sessionId>`) и счётчик `client_seq` (`funnel:seq:<sessionId>`) в localStorage на каждое изменение, но источник — копия в памяти: ошибка хранилища не роняет воронку. Остановленная (`dispose`) очередь больше не пишет в хранилище: поздний ответ не затрёт outbox новой очереди той же сессии, а оставшиеся подтверждённые события уйдут повторно как `duplicate`.
- Две вкладки одной сессии (id сессии общий в localStorage, §8.1): перед каждым событием очередь перечитывает сохранённый `client_seq` и берёт максимум, а при записи outbox сохраняет события другой вкладки, которых сама не подтверждала. Так `client_seq` не повторяется (иначе раздувался бы `out_of_order`), и одна вкладка не стирает outbox другой.
- Очередь при создании досылает outbox других сессий этого браузера (сессия истекла, `?variant=`, сброс): до 100 событий на сессию за раз, по одному запросу, и удаляет их ключи, когда сервер ответил за все события; при сетевой ошибке ключи остаются до следующего открытия, отказ 400/413 делит пачку пополам, пока отвергнутое событие не останется одно, и отбрасывается только оно. Если «чужая» сессия ещё жива в другой вкладке (вкладка 2 открыла `?variant=B`), её outbox тоже уйдёт и ключи удалятся; это безопасно: вкладка 1 держит outbox и счётчик в памяти и перезапишет их при следующем сохранении, а повторно отправленные события придут как `duplicate`. После `dispose()` досылка останавливается и хранилище не трогает. `dispose()` (уход из воронки внутри SPA, где нет `visibilitychange`) отдаёт непустой outbox в `sendBeacon`, ничего из него не удаляя.
- Страницы `/admin/*` отдаются только с Basic Auth (тот же guard, что у админского API): браузер спрашивает пароль один раз при открытии страницы и дальше сам прикладывает его к запросам API. Без этого первый же `fetch` получил бы 401 посреди отрисованной админки.
- `lib/query.ts` (аддитивно к `lib/` Фазы 3): `apiQuery(routeName, input)` строит опции TanStack Query с ключом `[routeName, input]`, поэтому разные фичи читают один маршрут из одного кеша, а мутация сбрасывает его по имени маршрута.
- Публикация и откат из командной палитры открывают страницу Versions с тем же диалогом подтверждения (`?publish=N`, `?rollback=1`), а не выполняются сразу: активная версия не меняется без подтверждения ни из одного места.
- Значок уведомлений в шапке ведёт на Live events с фильтром Rejected и не показывает красную точку: признака «есть непросмотренные отказы» у сервера нет, а точка без данных была бы ложным сигналом.
- Фильтры дашборда хранятся в URL (`?version=&variant=&campaign=&source=&period=&from=&qa=1`): отфильтрованный вид переживает refresh и им можно поделиться. Начало периода («Last 7 days») фиксируется в момент выбора, иначе ключ запроса менялся бы на каждом рендере.
- В Funnel journey переключатель варианта трёхпозиционный (Both / A / B): «оба» — это значение фильтра по умолчанию из контракта, и без него нельзя было бы вернуться к общей картине.
- Шаги и результаты в журнее подписаны по своим id («team_size» → «Team size»): id стабилен между версиями и знаком по конфигу, а полный текст вопроса показывается в поповере шага (из `GET /admin/versions/:v/preview`).
- Плитки результатов: «Reached result», «CTA clicked» и до четырёх результатов; если результатов больше, три самых частых и «Other results» с суммой остальных (сетка 2×3 эталона).
- Аватар «No UTM» в вырезе источников не нажимается: фильтр `source` в контракте — непустая строка, и отбор «без источника» сервер не поддерживает.
- Админка грузится отдельным чанком (`lazy` в router): бандл воронки не тянет дашборд, и сборка проходит без предупреждения о размере чанка.
- Дельта KPI к предыдущей версии («+3.1 pts vs v1») и плитка «Other results» считаются в дашборде из `versions[]` и `results[]` ответа: это разность и сумма двух чисел контракта для подписи, а не новая метрика; определения метрик остаются в `aggregate`.
- Панель Data quality не показывает строку «Accepted» и колонку «Last seen» эталона: в контракте нет этих чисел, а добавлять их ради подписи значило бы расширять ingest_log-запросы. Кнопки-иконки в шапках панелей ведут на связанные страницы (Live events с фильтром, Versions), а не изображают экспорт, которого нет.
- `b, strong` в `global.css` получают вес 600: правило §10 «никаких весов 700+», а браузерный `<b>` по умолчанию жирный. Треки полуколец A/B — токены `--a-track` / `--b-track` (смешение с `white`, как в эталоне: у `--card` явный оттенок 0, и смешение с ним уводит синий в сиреневый).
- Индикатор «Receiving events» в шапке админки держит своё SSE-соединение с `/api/live` и пульсирует, только если за последнюю минуту пришёл хотя бы один результат приёма (бэклог при подключении со старым временем не считается); при открытом, но тихом потоке пишет «Listening», без соединения — «Offline». На странице Live events открыто два потока: это дешевле, чем делить одно соединение между фичами через глобальный стор, которых нет. На узком экране (≤860px) индикатор не монтируется и поток не открывает.
- Контракт (аддитивно): у `LiveEntry` есть `seq` — номер, который шина Live events присваивает каждой записи; он только растёт и начинается от текущего времени в микросекундах, поэтому уникален и после перезапуска сервера. Это идентичность строки на странице Live events: одна пачка может содержать одно событие несколько раз с одним временем приёма, а бэклог, повторно присланный при переподключении, по `seq` отбрасывается. Страница хранит последние 200 строк.
- Очередь событий отправляет пачки через общий клиент `lib/api.ts` (один HTTP-клиент в приложении); отказ сервера приходит как `DomainError`, и очередь классифицирует его по HTTP-статусу ошибки. `sendBeacon` по-прежнему берёт путь из контракта: у beacon нет ответа, и общий клиент ему не нужен.
- Очередь живой сессии создаётся лениво (`createEventSink` в `tracking.ts`) и останавливается в cleanup эффекта `FunnelPage`: React может остановить и снова запустить эффекты (StrictMode, перемонтирование), остановленная очередь игнорирует события, поэтому следующая очередь подхватывает тот же outbox и `client_seq` из localStorage.
- Сборка веба выносит код из `node_modules` в отдельный чанк `vendor` (`codeSplitting.groups`): после подключения очереди основной чанк перешёл порог Vite в 500 кБ, а `pnpm build` должен проходить без предупреждений; заодно библиотеки кешируются отдельно от кода приложения.
- В e2e лимиты `RATE_LIMIT_SESSIONS` и `RATE_LIMIT_EVENTS` подняты до 600 в минуту (env `webServer` в `playwright.config.ts`): все тесты идут с одного IP, а лимит — защита от одного посетителя, его проверяют серверные тесты.
- Клиент не присылает `utm_*` в событиях (в §7.1 они необязательные): UTM сессии знает только сервер, в ответе сессии их нет, и сервер всё равно берёт их из строки сессии. Событие, пришедшее после закрытия очереди (переход, завершившийся после размонтирования), дописывается в outbox и отправляется одним beacon (`appendToOutbox`: без fetch, таймеров и подписок); beacon без ответа, поэтому событие остаётся в outbox до следующей очереди, созданной для сессии (уже открытая очередь его не подхватывает); живой остаётся только очередь смонтированной сессии.
- Синхронизация ветки фазы с `main` (PR «merge main into phase/…», #121) вливается merge commit, а не squash: так `main` остаётся предком ветки фазы, и итоговое слияние фазы в `main` не повторяет уже разрешённые конфликты. Задачи по-прежнему вливаются squash (§13.1).
- Диагностика времени плагинов Rolldown (`[PLUGIN_TIMINGS]`) в сборке веба отключена (`build.rolldownOptions.checks.bundlerTimings: false`; `pluginTimings` в Rolldown 1.2 устарел): она сообщает, что React Compiler (babel) занял большую долю сборки, зависит от загрузки машины, а не от кода, и делала `pnpm build` то с предупреждением, то без (§3.1). Порог размера чанков не тронут.
- Порог значимости A/B (α = 0.05) живёт в одной функции `isSignificant` из `shared/analytics/stats.ts` (аддитивный экспорт `@funnel/shared`): по ней и вердикт агрегатора, и бейдж в `AbPanel`, чтобы два определения «значимо» не разошлись.
