# Аналитика: правила агрегации

Все числа дашборда, ответ `GET /api/analytics/summary`, ground truth генератора и `pnpm verify` считает одна чистая функция `aggregate` из `packages/shared/src/analytics/aggregate.ts`. Сервер только выбирает строки из SQLite и передаёт их в неё. Форма ответа описана схемой `AnalyticsSummarySchema` (`packages/shared/src/analytics/summary.ts`).

## Единица счёта — уникальная сессия

Каждая сессия сворачивается в профиль из множеств: какие шаги она достигла, какие завершила, нажимала ли Back, дошла ли до результата. Поэтому дубли событий и порядок их прихода на числа не влияют.

Пример: сессия посмотрела `team_size`, нажала Back, снова посмотрела `team_size`. reached(team_size) = 1, а не 2.

Версия, вариант и UTM берутся из строки сессии, а не из событий.

## Профиль сессии

- **reached(step)** — есть `step_viewed`, `answer_submitted` или `step_completed` по этому шагу. Это правило implied reach: если шаг завершён, его видели, даже если `step_viewed` потерялся или пришёл позже. Начатая сессия без шаговых событий достигла первого шага: сессия создаётся, когда воронка его рисует.
- **reachedResult** — есть `result_viewed` или `cta_clicked`. Шаг `result` считается достигнутым ровно тогда.
- **clickedCta** — есть `cta_clicked`.
- **furthestIndex** — наибольшая позиция достигнутого шага в `stepSequence` варианта сессии. Позиция в последовательности, а не время последнего события, поэтому возвраты назад и порядок прихода её не меняют.
- **последняя активность** — наибольший `server_ts` событий сессии.

## Метрики

| Метрика            | Определение                                                                                                                                                                                                 |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Started            | сессии с `session_started` (событие пишет сервер, поэтому оно есть у каждой сессии)                                                                                                                         |
| Reached(step)      | сессии, достигшие шага                                                                                                                                                                                      |
| Completed(step)    | достигли шага и либо прислали по нему `step_completed`, либо достигли более позднего шага или результата                                                                                                    |
| Step pass rate     | Completed / Reached. Знаменатель — только те, кому шаг показали, поэтому метрика корректна для условных шагов                                                                                               |
| Dropped here(step) | сессии без результата, завершённые (см. ниже), у которых `furthestIndex` указывает на этот шаг. Начатая сессия, не приславшая ни одного шагового события, считается достигшей первого шага и ушедшей с него |
| In progress        | сессии без результата, которые ещё не завершены                                                                                                                                                             |
| Came back(step)    | сессии с `back_clicked`, у которого `destination_step_id` — этот шаг                                                                                                                                        |
| Result rate        | reachedResult / Started                                                                                                                                                                                     |
| CTA CTR            | clickedCta / reachedResult                                                                                                                                                                                  |
| Started → CTA      | clickedCta / Started — основная метрика эксперимента                                                                                                                                                        |
| Back usage         | доля сессий хотя бы с одним `back_clicked` (guardrail)                                                                                                                                                      |
| Branch split       | для условного шага: сессии, достигшие и шага-родителя, и условного шага, делённые на достигших родителя. Родитель — шаг, на ответ которого ссылается `visibleWhen`                                          |

Для каждой сессии верно: она либо дошла до результата, либо in progress, либо ушла ровно с одного шага. Поэтому Started = reachedResult + In progress + Σ Dropped here.

## Dropped или in progress

Порог — константа `IN_PROGRESS_WINDOW_MS` = 30 минут. Живая (`live`) сессия без результата, последняя активность которой была меньше 30 минут назад, — in progress, а не отвал: пользователь, возможно, ещё отвечает.

Порог применяется только к `live`. Синтетические сессии генератора и QA-сессии (override) считаются завершёнными сразу: иначе после запуска генератора его «брошенные» сессии полчаса висели бы в in progress, и `verify` расходился бы с ground truth.

## Фильтры

- **Версия** — по умолчанию активная. Пошаговые данные считаются только для одной версии: наборы шагов у версий разные.
- **Вариант** — A, B или оба. Для «оба» список шагов — последовательность A, а за ней шаги, которые есть только в B.
- **utm_campaign**, **utm_source** (вырез в Funnel journey), **период** (по времени создания сессии).
- **Include QA sessions** — сессии с override (`traffic_type = 'qa'`) скрыты по умолчанию. Синтетический трафик показывается.

Список источников (`sources`) не сужается фильтром по источнику: вырез показывает все источники, чтобы между ними можно было переключаться.

## A/B

Сравнение идёт всегда внутри выбранной версии (у версий разный `experiment.id`) и всегда по обоим вариантам, независимо от фильтра варианта.

- для каждого варианта: доля Started → CTA и 95% доверительный интервал Уилсона;
- разница B − A в процентных пунктах и p-value двустороннего z-теста двух пропорций (объединённая дисперсия);
- сколько сессий на вариант нужно, чтобы такая разница стала значимой при α = 0.05 и мощности 0.8;
- вердикт текстом. При p ≥ 0.05 он говорит «X is ahead by N points, but the difference is not significant yet». Слова «wins» нет никогда.

## Versions compared, Other events

- **Versions compared** — KPI по каждой опубликованной версии с теми же фильтрами (кроме версии).
- **Other events** — для каждого события каталога выбранной версии, которого нет среди семи базовых: число уникальных сессий с ним и доля среди сессий с кликом CTA. Список строится из каталога, поэтому новое событие новой версии появляется без изменения кода дашборда.

## Качество данных

- **duplicates** — сумма дублей из `ingest_log` за период;
- **rejected** — отклонённые события из `rejected_events` за период с разбивкой по причинам;

Эти два числа считаются по всему трафику за период: у строк приёма нет контекста сессии (отклонённое событие может не иметь сессии вовсе), поэтому фильтры версии, варианта, кампании, источника и QA к ним не применяются. Остальные два — по событиям выборки:

- **out of order** — события выборки с `flags_json.out_of_order` (при приёме `client_seq` был меньше уже принятого в сессии);
- **context mismatch** — события выборки, в которых клиент прислал версию, вариант или UTM, отличные от сессии.

## Сверка с генератором

Генератор — `scripts/generate-traffic.ts` и `scripts/lib/*`, сверка — `scripts/verify.ts`.

**Ground truth — это не данные сервера.** Генератор ведёт собственный журнал намерений: какие сессии он создал (версия, вариант, UTM, тип трафика), какие события собирался отправить, какие дубли и повторы пачек отправлял сознательно, какие отказы вызывал сам. Ожидаемые числа он считает **той же** функцией `aggregate` по этому журналу. Если бы ground truth считался по строкам сервера, сверка была бы тавтологией; так она проверяет весь конвейер: HTTP API, приём, дедупликацию, обогащение из сессии, выборку и агрегацию.

**Набор проверок.** Ground truth — список проверок, каждая из которых — фильтры и ожидаемая сводка в форме ответа `/api/analytics/summary`. Для каждой версии, которой коснулся прогон (проверка без единой сессии не создаётся: пустое ожидание совпало бы с пустым ответом, сервер такую отклоняет):

- фильтры по умолчанию (QA скрыт);
- `includeQa=true` (виден эффект 4 сессий с override);
- `campaign=spring_launch`;
- `variant=B`.

Каждая проверка ограничена окном прогона по часам сервера: `from` — точное время создания первой сессии (`expiresAt` из ответа минус TTL версии), `to` — последний заголовок `Date` плюс секунда (у заголовка секундная точность). Трафик до и после генератора на сверку не влияет. Каждая проверка указывает версию явно, иначе она сравнивалась бы с той версией, что активна в момент чтения.

**Где хранится.** Файл `--out` (по умолчанию `.generated/ground-truth.json`) и копия на сервере: генератор загружает его через `PUT /api/admin/ground-truth`, сервер хранит его в таблице `ground_truth` (последняя строка — актуальная).

**`pnpm verify [--base-url …] [--file .generated/ground-truth.json]`** запрашивает `/api/analytics/summary` для каждой проверки и сравнивает поле за полем общей функцией `compareSummaries` из `@funnel/shared`:

- счётчики — точно;
- доли — с допуском 1e-9;
- не сравниваются: `groundTruthMatches` (сама строка сверки), флаг `active` у версий и версии, которых нет в ожидаемой сводке (генератор перечисляет все опубликованные к концу прогона, так что пропускаются только опубликованные позже).

Выводит `OK` или список расхождений; при расхождении exit code 1.

**Строка в дашборде «Matches generator ground truth (last run, any filter): Yes / No».** Сервер берёт последнюю строку `ground_truth`, пересчитывает каждую проверку своим `aggregate` по базе и сравнивает тем же `compareSummaries`. Строка относится к последнему прогону целиком, а не к фильтрам, выбранным в дашборде. Если ничего не загружено, `groundTruthMatches = null` и в строке стоит «Not run». Ответ кешируется, пока не изменятся данные, загруженная ground truth или минута. Так сверка работает и на проде, где локального файла генератора нет.

**Чем проверено.** Интеграционный тест `scripts/verify.test.ts`: сервер в процессе на временной базе, генератор на 120 сессий с `--publish-next`, затем `verify` — 8 проверок без расхождений по v1 и v2, а подделанная ground truth (один клик CTA лишний) даёт расхождение с путём поля. `scripts/generator.test.ts` проверяет, что прогон проходит все ветки и результаты, даёт дубли, out of order, context mismatch и четыре причины отказа. E2E `e2e/generator.spec.ts`: после генератора дашборд показывает «Yes».

Почему синтетика не попадает в in progress: порог 30 минут применяется только к `live`, поэтому брошенные генератором сессии сразу считаются отвалом и совпадают с ground truth (см. выше).

## Ограничение

Агрегатор работает в памяти по всем строкам выборки. На объёмах тестового задания это быстро и легко проверяется; на больших объёмах это переводится в инкрементальные агрегаты (см. `docs/LIMITATIONS.md`).
