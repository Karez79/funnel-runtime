# События

Схема события, конверт пачки и причины отказа определены один раз в `packages/shared/src/events/schema.ts`, каталог и whitelist — в `events/catalog.ts`. Их используют клиентская очередь, приём на сервере и генератор.

## Схема клиентского события

`ClientEventSchema`:

| Поле                                                      | Тип                                | Смысл                                                                                     |
| --------------------------------------------------------- | ---------------------------------- | ----------------------------------------------------------------------------------------- |
| `event_id`                                                | uuid                               | uuid v7, создаётся вместе с событием и не меняется при повторах                           |
| `session_id`                                              | string                             | id сессии от сервера                                                                      |
| `name`                                                    | string                             | имя из каталога версии сессии                                                             |
| `client_timestamp`                                        | ISO datetime со смещением          | время клиента; не доверенное                                                              |
| `client_seq`                                              | целое ≥ 0                          | монотонный счётчик в сессии (`localStorage`, общий для вкладок)                           |
| `funnel_id`, `funnel_version`, `experiment_id`, `variant` | string, целое > 0, string, `A`/`B` | что клиент считает своим контекстом; сервер сравнивает с сессией, но хранит свои значения |
| `step_id`                                                 | string или `null`                  | шаг события                                                                               |
| `utm_source`, `utm_medium`, `utm_campaign`                | string, необязательные             | только для проверки расхождения                                                           |
| `properties`                                              | объект                             | свойства; ключи вне whitelist отбрасываются                                               |

Конверт пачки: `{ batch_id?: string (1–100 символов), events: unknown[] (до 100) }`, тело до 256 КБ. Элементы `events` намеренно не типизированы в конверте: каждое событие проверяется отдельно, поэтому одно битое не роняет пачку.

## Каталог версии и whitelist

Каталог — `events.allowed` **закреплённой версии сессии**: список `{ name, trigger, properties[] }`. Событие с именем не из каталога отклоняется (`unknown_event`). Каждая версия обязана содержать семь базовых событий (`BASE_EVENTS`, проверяет линт), на которых определена аналитика. Новая версия может добавить событие; оно принимается только от сессий этой версии. Так во второй итерации (Фаза 7) появляется `recommendation_expanded`: сессии старых версий его не отправляют, а дашборд показывает его в Other events без изменения кода.

Свойства фильтруются `filterProperties`:

- остаются только ключи из `properties` определения события, со скалярными значениями (`string`, `number`, `boolean`, `null`);
- `answer_kind` принимается, только если это форма ответа (`single_select`, `multi_select:<N>`, `number`), иначе отбрасывается;
- `events.privacy.allowAnswerKinds: false` убирает `answer_kind` из whitelist;
- отброшенные ключи не роняют событие, а перечисляются в `flags_json.dropped_props`.

Это и есть защита приватности: у сырого ответа нет ключа, под которым он мог бы попасть в базу. `events.privacy.storeRawAnswers = false` во всех конфигах, `true` — ошибка линта.

`answerKind(step, value)` возвращает только форму ответа. Ветки видны в аналитике по `step_viewed` условных шагов (например, `office_days`), значения для этого не нужны.

## Когда шлётся какое событие

| Событие                                     | Когда                                                                 | `step_id`            | `properties`                                            |
| ------------------------------------------- | --------------------------------------------------------------------- | -------------------- | ------------------------------------------------------- |
| `session_started`                           | сервер, в транзакции создания сессии                                  | `null`               | —                                                       |
| `step_viewed`                               | шаг отрисован, каждый раз (и после Back, и после refresh)             | шаг                  | `step_type`, `visible_step_index`, `visible_step_count` |
| `answer_submitted`                          | валидный ответ отправлен                                              | шаг                  | `answer_kind`                                           |
| `step_completed`                            | переход вперёд с валидного интерактивного шага (для `info` не шлётся) | шаг                  | `next_step_id`                                          |
| `back_clicked`                              | кнопка Back, `Esc`/`Alt+←` или браузерная «назад»                     | шаг, с которого ушли | `destination_step_id`                                   |
| `result_viewed`                             | результат отрисован                                                   | `result`             | `result_id`                                             |
| `cta_clicked`                               | клик по основной CTA                                                  | `result`             | `result_id`, `action`                                   |
| `recommendation_expanded` (вторая итерация) | после CTA раскрыт подробный план                                      | `result`             | `result_id`, `action`, `source` (`result_cta`)          |

`session_started` пишет только сервер: `event_id = 'srv:session_started:' + sessionId`, `origin = 'server'`, `client_ts = server_ts`. Поэтому Started в аналитике гарантирован для каждой сессии.

Хелпер `track(name, stepId, properties)` на клиенте отправляет событие, только если `name` есть в каталоге версии **текущей сессии**, иначе молча пропускает. В режиме предпросмотра версии события не отправляются вообще.

## Приём: `POST /api/events/batch`

Алгоритм (`apps/server/src/modules/events/service.ts`):

1. Разбирается конверт. Кривой конверт — 400; валидный — **всегда 200**, даже если все события отклонены.
2. Каждое событие проверяется отдельно, по порядку:
   1. `ClientEventSchema` → иначе `invalid_event`;
   2. сессия существует → иначе `unknown_session`;
   3. имя есть в каталоге закреплённой версии → иначе `unknown_event`;
   4. событие не серверное → `session_started` от клиента отклоняется как `server_only`;
   5. `step_id`, если не `null`, входит в последовательность **варианта** сессии → иначе `unknown_step`;
   6. свойства фильтруются по whitelist.
3. Обогащение из сессии: `funnel_version`, `experiment_id`, `variant`, `utm_*` берутся из строки сессии. Если клиент прислал другое, сохраняются серверные значения и ставится флаг.
4. Вся пачка вставляется одной транзакцией: `INSERT … ON CONFLICT(event_id) DO NOTHING`. Ноль изменённых строк — статус `duplicate`. Отклонённые пишутся в `rejected_events`, итог пачки — в `ingest_log`.
5. Ответ: `{ results: [{ event_id, status: 'accepted' | 'duplicate' | 'rejected', reason? }], accepted, duplicates, rejected }` в порядке элементов пачки. `event_id` равен `null`, если у элемента не было читаемого id.
6. После коммита результаты по каждому элементу уходят в шину Live events (`GET /api/live`, SSE).

События истёкшей сессии принимаются: сессия существует, а outbox и `sendBeacon` законно досылают события после паузы.

Следствия, которые проверяет тест 3: повтор того же `event_id` в одной пачке, в двух пачках или повтор всей пачки даёт одну строку и статусы `duplicate`; одно битое событие не мешает остальным; порядок прихода не важен.

### Причины отказа (`REJECT_REASONS`)

| Причина           | Когда                                                                                          |
| ----------------- | ---------------------------------------------------------------------------------------------- |
| `invalid_event`   | событие не проходит `ClientEventSchema` (нет `event_id`, неверный тип поля, элемент не объект) |
| `unknown_session` | сессии с таким id нет                                                                          |
| `unknown_event`   | имени нет в каталоге закреплённой версии сессии                                                |
| `server_only`     | клиент прислал `session_started`                                                               |
| `unknown_step`    | `step_id` не входит в последовательность варианта сессии                                       |

### Флаги (`flags_json`)

| Флаг               | Когда ставится                                                                                                                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `context_mismatch` | клиент прислал `funnel_id`, `funnel_version`, `experiment_id` или `variant`, отличные от сессии, или **непустой** UTM, отличный от сессии (отсутствие UTM — не расхождение: после refresh клиент их не знает) |
| `out_of_order`     | `client_seq` меньше максимального, уже принятого в сессии на момент вставки, включая события раньше в той же пачке; дубль на флаг не влияет                                                                   |
| `dropped_props`    | список ключей свойств, отброшенных whitelist                                                                                                                                                                  |

Флаги — только данные для панели качества. Метрики считаются по множествам сессий, поэтому порядок прихода на них не влияет.

## Клиентская очередь (`apps/web/src/features/funnel/eventQueue.ts`)

- **Outbox.** Событие получает `event_id` и `client_seq` при создании и сразу попадает в outbox в `localStorage` (`funnel:events:<sessionId>`, счётчик — `funnel:seq:<sessionId>`). Рабочая копия в памяти, хранилище — зеркало: переполненный или запрещённый `localStorage` не ломает воронку.
- **Отправка.** Флаш каждые 2 секунды или сразу при 10 событиях в outbox; пачка до 100 событий.
- **Что удаляется.** Только события со статусом `accepted` или `duplicate`. `rejected` удаляется с `console.warn` (повтор ответ не изменит). События, о которых ответ молчит, остаются.
- **Повторы.** Сетевая ошибка, 5xx, 429, нераспознанный ответ 200 — повтор с тем же `event_id` и задержкой 1, 2, 4, 8, 16, 30 с (дальше 30); после успеха задержка сбрасывается.
- **Ядовитая пачка.** 400 или 413 на пачку: очередь делит её пополам и шлёт снова; событие, которое сервер не принимает и в одиночку, удаляется с предупреждением. Иначе одно слишком большое событие навсегда блокировало бы outbox.
- **`sendBeacon`.** При `visibilitychange → hidden` и при уходе из воронки внутри SPA непустой outbox отправляется через `navigator.sendBeacon`. Ответа у beacon нет, поэтому события **остаются** в outbox и уйдут ещё раз при следующем флаше или визите; сервер ответит `duplicate`. Ровно для этого нужна дедупликация по `event_id`.
- **После refresh** outbox досылается. Очередь также досылает outbox других сессий этого браузера (истёкшая сессия, `?variant=`, сброс) и удаляет их ключи, когда сервер ответил за все события.
- **Две вкладки одной сессии.** Перед каждым событием очередь перечитывает сохранённый `client_seq` и берёт максимум, а при записи outbox сохраняет события другой вкладки. `client_seq` не повторяется, и одна вкладка не стирает outbox другой.

## Вторая итерация: `recommendation_expanded`

Событие появляется только в каталоге v3 (`events.allowed`), со свойствами `result_id`, `action`, `source`. Клиент шлёт его один раз после клика по CTA с `action: expand_recommendation`, когда раскрывается план на 30 дней: `result_id` и `action` — из CTA результата, `source = result_cta` (план открывается только этой кнопкой). Оба значения — `EXPAND_RECOMMENDATION` из `@funnel/shared`, им же пользуется генератор, который повторяет поведение клиента.

- Сессия v1/v2 событие не отправляет: `track` проверяет каталог версии сессии. Если такое событие всё же придёт от сессии v1/v2 (старый бандл, ручной запрос), ingest отклонит его с `unknown_event`.
- Лишние свойства отбрасываются по whitelist и попадают в `flags_json.dropped_props`, как у всех событий.
- Дашборд показывает его в панели Other events для v3 (уникальные сессии и доля от сессий с CTA): список строится из каталога выбранной версии, код дашборда для этого не менялся.
- Схема таблицы `events` не меняется: имя — строка, свойства — `props_json`.

Проверяется тестами `apps/server/src/iteration2.test.ts` (принимается от v3, отклоняется от v2, Other events) и сценарием `pnpm demo:iteration2`.
