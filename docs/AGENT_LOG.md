## Phase 0 — scaffold, quality gates, deploy

**Схема работы.** Основной агент (Claude Code, Opus 5.5) ведёт фазу: issues в milestone, ветка `phase/0-foundation`, на каждую задачу ветка `task/0.N-*` и PR в ветку фазы. Каждый PR ревьюит отдельный субагент с промптом из `.claude/agents/reviewer.md`. Он работает только на чтение, в собственном `git worktree`, и оставляет в PR комментарий с таблицей находок `blocker`/`major`/`minor`. Пока шло ревью одной задачи, основной агент делал следующую.

Субагент `reviewer` создан в этой же сессии, поэтому как именованный тип агента ещё не загружен. Ревью запускались как `general-purpose` агент с инструкцией прочитать и выполнить `reviewer.md`.

Что ревьюер реально запускал, зависело от PR. В #10 `pnpm check` ещё не существовал. В #11–#14, #16–#18 он сам гонял `pnpm check` (и `pnpm e2e` начиная с #14) в своём worktree. В #15 он опирался на прогон CI и пробное слияние.

**Повторное ревью.** В #10–#16 исправления по находкам проверялись только `pnpm check` (и CI с #15), повторного ревью не было: например, фикс #10 закоммичен в 13:24:41 и влит в 13:24:54. CI не существовал до #15, поэтому #10–#14 вливались без него. Человек спросил, кто ревьюит код, и это слабое место всплыло. С #18 правило такое: если в PR есть `blocker` или `major`, после исправлений запускается повторное ревью (re-review mode в `reviewer.md`), и слияние происходит только при вердикте APPROVE.

**Что нашли сами ворота.** Первый прогон e2e нашёл баг: `@fastify/static` падал на относительном `WEB_DIST`. Stop-хук один раз заблокировал завершение ответа, когда ветка фазы была красной после #14.

**Ошибка процесса.** PR #14 был влит, хотя `pnpm check` был красным: knip ругался на default-экспорт `e2e/global-teardown.ts`. Вывод проверки не был прочитан перед слиянием, а CI ещё не существовал и не мог заблокировать слияние. Исправлено в #16. Вывод: слияние только при зелёном CI и включённой защите `main`, а локально проверка и слияние идут одной командой (`pnpm check && gh pr merge`).

**Побочный эффект ревьюера.** При ревью #17 субагент выполнил `docker image prune -f`, удалив все висячие образы на локальном Docker-демоне, а не только свои. В `reviewer.md` добавлен запрет на глобальные команды очистки.
