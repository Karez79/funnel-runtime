# A/B-эксперимент

## Гипотеза

Вариант B начинает с простых категориальных вопросов (как работает команда, насколько разнесены часовые пояса) и откладывает числовые вопросы, которые требуют подсчёта (размер команды, число инструментов). Результат в B сформулирован как конкретная проблема команды, а CTA обещает план на 30 дней. Мы ожидаем, что меньшая когнитивная нагрузка в начале снизит ранний отвал, а конкретная формулировка результата повысит клики по CTA.

Порядок шагов в первой итерации:

| Версия | Вариант A                                                                                                              | Вариант B                                                                                                              |
| ------ | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| v1     | intro, team_size, work_mode, priorities, timezone_span, office_days, async_maturity, tool_count, result                | intro, work_mode, timezone_span, team_size, async_maturity, priorities, office_days, tool_count, result                |
| v2     | intro, team_size, work_mode, priorities, timezone_span, office_days, meeting_hours, async_maturity, tool_count, result | intro, work_mode, meeting_hours, timezone_span, team_size, async_maturity, priorities, office_days, tool_count, result |

`office_days` показывается только при `work_mode` hybrid или office. Тексты шагов и результатов B задаются `stepOverrides` и `resultOverrides` в конфиге.

## Метрики

- **Основная:** доля сессий, нажавших основную CTA, от всех начавших (started → CTA), по уникальным сессиям.
- **Вторичные:** result rate (дошли до результата / начали), CTR CTA (кликнули / увидели результат), отвал на первых двух вопросах варианта.
- **Guardrails:** доля сессий с хотя бы одним возвратом назад; распределение результатов (B не должен смещать рекомендации).

Определения метрик — в [`ANALYTICS.md`](ANALYTICS.md).

## Назначение и анализ

- Вариант назначает сервер: `fnv1a32(sessionId + ':' + experimentId) % 100` против кумулятивных весов (50/50). Назначение сохраняется в сессии и больше не пересчитывается.
- `?variant=A|B` создаёт QA-сессию с override; такие сессии по умолчанию исключены из дашборда.
- Для основной метрики дашборд показывает по каждому варианту долю и 95% доверительный интервал Уилсона, разницу B − A в процентных пунктах, p-value двустороннего z-теста двух пропорций и сколько сессий на вариант нужно, чтобы такая разница стала значимой (α = 0.05, мощность 0.8).
- Вердикт текстом и честно: при p ≥ 0.05 — «B is ahead by X points, but the difference is not significant yet». Решение о победителе — только при p < 0.05 и достаточной выборке.

## Ограничения

- A/B сравнивается только внутри одной версии: `experiment.id` у версий разный (`…-v1`, `…-v2`), и наборы шагов тоже.
- Данные на демо-стенде в основном синтетические. Генератор закладывает эффект намеренно: в варианте B вероятность уйти на первых двух вопросах ниже, а вероятность клика по CTA выше. Поэтому разница между вариантами на дашборде демонстрирует работу расчёта, а не продуктовый вывод.
- Синтетические сессии видны в дашборде по умолчанию (иначе генератор бесполезен); живые пользователи на проде смешиваются с ними в одной выборке, если не сузить период.
