## Вторая итерация (Фаза 7)

**Честно о v3.** `configs/funnel-v3.json` лежал в репозитории с самого начала, вместе с v1 и v2; время его «получения» не выдумываем. До Фазы 7 его не сидили, не публиковали, тесты и код на файл не ссылались. Событие `recommendation_expanded` при этом было в коде с Фаз 3–4 (отправка в `ResultScreen.tsx`, тесты каталога и ingest): его описывает сама спецификация (CLAUDE.md §7.5, §8.2), и оно с самого начала отправлялось только если есть в каталоге версии сессии, так что для v1/v2 это была проверка «не отправлять», а не подгонка под v3. Ценность второй итерации не в том, что конфиг пришёл неожиданно, а в двух проверяемых вещах: код под v3 заранее не подгонялся (движок, линт, diff, каталог и дашборд справились с ним без изменений, см. ниже), и v3 уходит на работающий прод через админский API без передеплоя и без изменения схемы БД.

**Шаг 1 — загрузка на прод (оркестратор, 2026-10-02 05:19:50 MSK; `created_at` v3 на проде — `2026-10-02T02:19:50.115Z`).** `POST /api/admin/versions` с `configs/funnel-v3.json` создал черновик v3. Линт: 0 ошибок, 3 предупреждения — добавлен результат `regulated_scale`; добавлено событие `recommendation_expanded`; в варианте B удалён шаг `tool_count`. Diff против активной v2: id эксперимента сменился на `question-order-and-result-framing-v3` (A/B начинается заново); результат `regulated_scale` и правило №1 для него (зависит от `priorities`, `security_constraints`); событие `recommendation_expanded`; шаг `security_constraints` добавлен в A и B; `tool_count` удалён из B; у `priorities` изменились опции (добавлен `compliance`); изменены тексты и CTA варианта B.

**Шаг 2 — что пришлось дописать.** Код первой итерации проверен против v3 тестами (`packages/shared/src/iteration2.test.ts`) и ревьюером, который прошёл ветку compliance в браузере на обоих вариантах.

Без изменений (уже работало): схема конфига; линт и diff; оператор `contains`, открывающий `security_constraints`; пересчёт прогресса; правило результата `regulated_scale` первым; игнорирование ответа скрытого шага; вариант B без `tool_count`; каталог версии на клиенте (`track`) и в ingest; whitelist свойств; блок «неделя» для неизвестного результата просто не показывается; бейдж условия в дашборде («if priorities includes compliance»); панель Other events из каталога; схема БД.

Изменено, каждое — отдельным коммитом с причиной (#158):

1. `fix(web)`: клиент не отправлял свойство `source`, которое каталог v3 разрешает у `recommendation_expanded`; теперь `source = result_cta`.
2. `fix(generator)`: генератор не повторял это событие клиента, поэтому прогон на v3 не наполнял Other events и ground truth не мог их проверить; теперь шлёт после клика CTA, если событие есть в каталоге версии сессии (прогоны на v1/v2 не меняются).
3. `refactor(shared)`: значения `action` и `source` вынесены в `EXPAND_RECOMMENDATION`, чтобы клиент и генератор не расходились (minor ревьюера).

Для демонстрации добавлены `GET /api/admin/schema` (отпечаток схемы для проверки по HTTP) и `pnpm demo:iteration2` (#164). Ни одной миграции в фазе нет.

**Шаг 3 — тесты, которым нужен v3 (#160).** Снимок `sqlite_master` и число миграций одинаковы до и после загрузки, публикации и отката v3; сессия v2 варианта B, остановленная на `tool_count`, после публикации v3 доходит до результата на v2 (с формулировками B из v2), а новые сессии B получают v3 без `tool_count`; `recommendation_expanded` принимается от сессии v3 и отклоняется (`unknown_event`) от сессии v2.
